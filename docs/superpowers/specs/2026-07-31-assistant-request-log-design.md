# 事務補佐依頼台帳 ポータル内製化 設計書

- 日付: 2026-07-31
- 対象: 学科ポータル（department-portal）

## 背景・目的

現在、助手室（事務補佐）への依頼は、ダッシュボードの「助手室への依頼（Excel）」カードから、SharePoint/OneDrive上のExcelファイル（`docs/事務補佐依頼表（クラウド）.xlsx`が参照コピー）を開いて記入する運用になっている。OneDriveの接続が不安定になると依頼自体ができなくなる問題があるため、この依頼台帳をポータル（Firebase Hosting + Firestore）上に内製し、OneDriveへの依存をなくす。

現行Excelファイルは年度ごとにシートが分かれており（令和6年度／令和7年度／令和8年度、各約225〜230行）、列構成は以下の通り。

```
No | 依頼日 | 依頼者 | 依頼内容 | 依頼詳細 | 締切日 | 受託状況 | 担当者 | 完了日 | 所要時間 | 備考
```

依頼者が新規依頼を記入し、後から助手が受託状況・担当者・完了日・所要時間・備考を追記していく「共同編集の台帳」である点が、他の申請フォーム（一度きりの提出）と異なる。

## スコープ

**含む**
- 令和8年度（当年度）以降の新規依頼の記録・編集・削除
- 年度タブによる過去年度データの閲覧（今回の実装以降に蓄積される分）
- 絞り込み条件付きのExcelエクスポート
- ダッシュボード／サイドバーからの導線差し替え

**含まない（明示的に対象外）**
- 令和6・7年度分の過去データ（Firestoreへの移行はしない。既存Excelファイルはそのままアーカイブとして残す）
- リアルタイム同時編集（`onSnapshot`は採用しない。詳細は「データ取得方式」参照）
- ログイン・権限管理（既存アプリ全体と同様、認証なしの内部限定運用を踏襲）

## データモデル

新規Firestoreコレクション: `assistant_requests`

依頼1件 = 1ドキュメント（既存の`concurrent_works`コレクションと同じ設計パターン）。

| フィールド | 型 | 必須 | 説明 |
|---|---|---|---|
| `fiscalYear` | number | ○ | 依頼日から自動算出する令和年度（4月始まり）。例: 2026-05-01 → `8`。作成時に確定し、以後変更しない |
| `no` | number | ○ | 年度内の連番。追加時に「その年度の最大`no` + 1」（無ければ1）をクライアント側で計算して採番 |
| `requestDate` | string (`YYYY-MM-DD`) | ○ | 依頼日 |
| `requester` | string | ○ | 依頼者 |
| `category` | string | ○ | 依頼内容。選択肢: `その他` / `座席表作成` / `座席表貼り出し` / `印刷(講義)` / `印刷(講義以外)` / `試験監督` |
| `detail` | string | ○ | 依頼詳細（自由記述） |
| `deadline` | string (`YYYY-MM-DD`) | ○ | 締切日 |
| `status` | string | ○ | 受託状況: `未対応`（新規作成時の初期値）/ `受託中` / `完了` |
| `assignee` | string | - | 担当者（自由入力。「助手全員」のような値も許容） |
| `completedDate` | string (`YYYY-MM-DD`) | - | 完了日 |
| `duration` | string | - | 所要時間（「20分」のような自由記述。現行Excelの表記を踏襲） |
| `notes` | string | - | 備考 |
| `createdAt` | serverTimestamp | ○ | 作成日時（監査用） |
| `updatedAt` | serverTimestamp | ○ | 最終更新日時（編集の度に更新） |

`no`の採番は「その年度のドキュメントを`no`降順1件取得して+1」をクライアント側で行う。トランザクションは使わない。同時投稿による連番の重複は稀にあり得るが、他フォームと同様の非トランザクション実装で許容する（`no`はあくまで人間向けの参照番号で、Firestoreドキュメント自体がID的な役割を持つため、重複しても実害は小さい）。

## 画面構成・ルーティング

新規ファイル `src/AssistantRequestPage.jsx`、ルート `/assistant-requests` を1つ追加する（`src/App.jsx`の`<Routes>`に追記）。新規依頼フォームと一覧表示は別ページに分けず、同一ページ内に同居させる。

画面は上から以下の構成:

### 1. 年度タブ
- 存在する`fiscalYear`の一覧＋常に「当年度」を含めて自動生成（当年度は依頼が1件もなくても常にタブとして表示）。
- デフォルト選択は当年度。
- 年度の切り替えは完全自動判定（依頼日から算出した`fiscalYear`に基づく）。「新年度を開始」のような手動操作は設けない。新年度最初の依頼が登録された時点で、該当年度のタブが自動的に選択肢に追加される。

### 2. 新規依頼フォーム（折りたたみ式）
- 「＋ 新規依頼を追加」で展開する入力フォーム。既存の申請フォーム（`ConcurrentWorkForm`等）と同じ見た目・入力コンポーネントを踏襲する。
- 入力項目: 依頼日（初期値: 本日）／依頼者／依頼内容（選択式、上記6種）／依頼詳細（テキストエリア）／締切日。
- 送信時の処理:
  1. 依頼日から`fiscalYear`を算出
  2. 該当年度の最大`no`を取得し+1
  3. `status: '未対応'`を付与し`addDoc`
  4. フォームを閉じ、一覧を再取得

### 3. 一覧表
- 選択中の年度タブに属するドキュメントを`no`昇順で表示（`getDocs`で`where('fiscalYear','==', 選択年度) orderBy('no')`）。
- 列: No / 依頼日 / 依頼者 / 依頼内容 / 依頼詳細 / 締切日 / 受託状況（バッジ表示: 未対応=グレー・受託中=黄・完了=緑）/ 担当者 / 完了日 / 所要時間 / 備考 / 削除ボタン。
- 行（削除ボタン以外の部分）をクリックすると編集モーダルが開く。

### 4. 編集モーダル
- 全フィールド（依頼者側の項目・助手側の項目すべて）を編集可能にする。誤記修正や受託状況の更新など、あらゆる編集をこのモーダルから行う。
- 保存時: `updateDoc`で該当ドキュメントを更新し、`updatedAt`を`serverTimestamp()`で更新。モーダルを閉じ、一覧を再取得。
- 注意: `fiscalYear`と`no`は作成時に確定した値のまま変更しない。モーダルで依頼日を修正しても（年度をまたぐ日付に直した場合も）、その依頼が属する年度タブや連番は再計算しない。

### 5. 削除
- 各行に削除ボタンを設置。既存の`ConcurrentWorksList`と同じ`window.confirm`による確認ダイアログを経てから`deleteDoc`。

## データ取得方式

Firestoreの`onSnapshot`（リアルタイム購読）は採用せず、既存の一覧コンポーネント（`ConcurrentWorksList`等）と同じ「`getDocs`でマウント時に取得し、追加・編集・削除のたびに再取得する」方式に統一する。

判断理由:
- 既存コードベースに`onSnapshot`パターンが存在せず、導入すると購読のライフサイクル管理（年度タブ切り替え時の再購読/解除）やエラーハンドリングの経路が増え、一貫性が崩れる。
- リアルタイム反映されないことによる不便（他の人の変更がすぐ見えない）はあるが、今回の課題である「OneDriveが不安定で繋がらなくなる」問題はFirestore化自体で解消される。
- リアルタイム化しても、同一行を同時編集した場合の後勝ち上書きという同時編集の根本的な衝突は解決しない。

## エクスポート

- 一覧上部に「エクスポート」ボタンを設置。押すと絞り込みパネルを表示する。
- 絞り込み項目（すべて任意）: 依頼日の期間（開始〜終了）／受託状況／担当者。
- 「ダウンロード」実行時、現在選択中の年度タブのデータに対してクライアント側でフィルタを適用し、`exceljs`で現行Excelと同じ列構成（No/依頼日/依頼者/依頼内容/依頼詳細/締切日/受託状況/担当者/完了日/所要時間/備考）のワークブックを生成、`file-saver`でダウンロードする（実装パターンは`PrinterForm.jsx`のExcel生成処理を踏襲）。
- シート名: 選択中の年度名（例: `令和8年度`）。
- ファイル名: `事務補佐依頼一覧_<年度名>.xlsx`（例: `事務補佐依頼一覧_令和8年度.xlsx`）。

## エラーハンドリング

既存フォーム・一覧コンポーネントの流儀を踏襲する。新しい通知UI・リトライ機構は導入しない。

- 一覧取得・追加・更新・削除はすべて`try/catch`で囲み、失敗時は`console.error`＋画面内にエラーメッセージを表示する。
- 削除は`window.confirm`による確認を必須とする。

## 既存ページとの接続

`src/App.jsx`:
- ダッシュボードの「助手室への依頼（Excel）」カードを、外部SharePointリンクから`navigate('/assistant-requests')`による内部遷移ボタンに置き換える。見た目は他の申請カード（学外非常勤講師兼務申請など）に揃える。
- `Sidebar`コンポーネントに、「非常勤講師一覧」「兼業一覧」と同じ並びで「事務補佐依頼一覧」へのリンクを追加する。
- `<Routes>`に`/assistant-requests`ルートを追加し、`AssistantRequestPage`をマウントする。

SharePoint上の元のExcelファイル自体は削除・変更しない（過去年度データのアーカイブとして残す）。ポータルからのリンクのみ、この新ページに一本化する。

## 対象外・今後の課題

- 令和6・7年度の過去データ移行（必要になった場合は別途インポートスクリプトを検討する）
- ログイン・権限に応じた編集制限（現状アプリ全体が認証なしのため、今回もその前提を踏襲）
- 同時編集時のリアルタイム反映・競合検知（`getDocs`方式を選んだトレードオフとして許容）
- セキュリティ上のトレードオフ: 本機能により、従来SharePoint/テナント認証の裏に置かれていたデータが、本アプリの他コレクションと同様の全面公開型`assistant_requests` Firestoreコレクションに移った。さらに、読み取り中心の`notices`コレクションと異なり、バージョン履歴のない台帳に対して匿名の削除操作も公開されている。アプリ全体の認証状況が近い将来に是正されない場合、Firestoreの定期エクスポート／バックアップを設定することで、誤操作または悪意による一括削除のリスクを軽減できる。

## 検証計画（手動）

1. `npm run dev`でローカル起動し、`/assistant-requests`を開く。
2. 新規依頼フォームから1件登録し、当年度タブに表示されること、Firestoreコンソールに正しいフィールド（`fiscalYear`, `no`など）で保存されていることを確認する。
3. 一覧の行をクリックして編集モーダルを開き、受託状況・担当者などを更新して保存、一覧に反映されることを確認する。
4. 削除ボタンから確認ダイアログ経由で1件削除し、一覧から消えることを確認する。
5. エクスポートボタンから絞り込み条件（期間／受託状況／担当者）を指定し、ダウンロードされた`.xlsx`の列構成・内容が正しいことを確認する。
6. ダッシュボードの「助手室への依頼」カードとサイドバーのリンクから`/assistant-requests`に正しく遷移できることを確認する。
